# `@ramon-sg/runner` 1.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Verificar que Bun puede ser el ejecutor por defecto (etapa 0) y publicar `@ramon-sg/runner` 1.0: la biblioteca que lee y escribe `.agents/runner.json` y arma el comando `bunx --bun` / `npx --yes` de cada herramienta.

**Architecture:** Biblioteca TypeScript compilada con `tsc` a ESM en `dist/`, sin dependencias en tiempo de ejecución y solo con APIs `node:*` que Bun también tiene. Un módulo por responsabilidad: archivo, versiones, comando, ejecutor, scripts, revisiones. Los tests corren el `dist/` compilado con `node --test`, y CI los corre con Node y con Bun.

**Tech Stack:** TypeScript 5.9, Node ≥ 20 (24 en desarrollo, `.tool-versions`), Bun ≥ 1.2, `node:test`, GitHub Actions, npm con procedencia.

**Spec:** `ramon-sg/agent-kitchen` → `docs/superpowers/specs/2026-11-20-bunx-runner-design.md` (hoy en `/Users/ramon/Projects/ramon-sg/agent-kitchen/.claude/worktrees/bunx-runner/docs/superpowers/specs/2026-11-20-bunx-runner-design.md`, rama `feat/bunx-runner`). Secciones: "El archivo", "El paquete `@ramon-sg/runner`", "API pública (1.0)", "Orden entre repos" (etapa 0 y paso 1).

## Global Constraints

- Nombre en npm: `@ramon-sg/runner`, siempre con scope. Repo: `ramon-sg/runner`.
- Descripción en npm y primera línea del README, literal: "Lee `.agents/runner.json` y arma el comando para correr cada herramienta con Bun o Node".
- Archivo: `.agents/runner.json`. Claves: `$schema`, `runner` (`"bun"` | `"node"`), `tools` (paquete → versión exacta). Sin `runner`, el efectivo es `"bun"`.
- Versión exacta = `X.Y.Z` con prerelease opcional, sin metadata de build. Nunca un rango.
- Comando: `bun` → `bunx --bun <paquete>@<versión> <args>`; `node` → `npx --yes <paquete>@<versión> <args>`.
- `$schema` escrito: `https://cdn.jsdelivr.net/npm/@ramon-sg/runner@<versión de la biblioteca>/runner.schema.json`.
- Claves desconocidas de `runner.json` se conservan al escribir y no hacen fallar la lectura. El formato solo crece con campos opcionales desde la 1.0.
- `dependencies` vacío en el `package.json` publicado.
- Ningún commit, push, release ni publicación sin el OK del usuario para esa acción.

## Review Focus

1. `runner.json` con JSON roto, `runner` desconocido (`"deno"`) o una versión en rango (`"^1.0.0"`): `RunnerFileError` con la ruta, nunca un `TypeError` ni un valor a medias. → Task 2.
2. Un `package.json` que ya tiene un script con el mismo nombre y otro contenido (`"issue:start": "make start"`): no se pisa y vuelve en `clashes`. → Task 6.
3. Argumentos con espacios o comillas (`--title "Fix it's broken"`) en `toolCommandText`: el texto, pegado en una shell, pasa los mismos argumentos. → Task 4.
4. `setTool` con una versión más baja que la escrita (`1.2.0` sobre `1.3.0`): no la baja sin `allowLower`. → Task 3.
5. Una máquina sin Bun y sin terminal: `chooseRunner` devuelve `node` con un aviso, no se cuelga esperando respuesta. → Task 5.
