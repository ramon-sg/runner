# Spike de la etapa 0: ¿puede Bun ser el ejecutor por defecto?

Fecha: 2026-11-20. Bun 1.4.4 y Node 24.14.1, fijados en `.tool-versions` (asdf). Para observar la caché se usó un directorio dedicado por prueba (`BUN_INSTALL_CACHE_DIR=<tmp>`), de modo que se ve qué descarga cada comando. Para los directorios temporales fuera del repo se exportó `ASDF_BUN_VERSION=1.4.4 ASDF_NODEJS_VERSION=24.14.1`.

## Step 1: paquete de prueba

`spike/probe/cli.js` (`#!/usr/bin/env node`, imprime `bun` o `node`), `package.json` con `bin.probe`, `npm pack` genera `probe-0.0.0.tgz`.

Respuesta: paquete armado.

## Step 2: ¿`--bun` gana sobre el shebang de Node?

```
bun add <ruta>/probe-0.0.0.tgz
bun x probe          -> node
bun x --bun probe    -> bun
bunx --bun probe     -> bun
```
(Node de asdf en el PATH: `~/.asdf/shims/node`.)

Respuesta: sí; sin `--bun` imprime `node`, con `--bun` imprime `bun`. El plan sigue.

## Step 3: ¿una herramienta real corre con `bunx --bun`?

```
bunx --bun @ramon-sg/github-rest@0.6.0 --help   -> exit 0, imprime "Usage: github-rest issue-work ..."
bunx --bun @ramon-sg/issue-flow@0.5.1 --help    -> exit 0, imprime "Uso: issue-flow issue branch ..."
```
Con caché vacía: "Resolved, downloaded and extracted [4]" / "[7]". No hubo errores de APIs de Node (stderr vacío en la segunda corrida).

Respuesta: sí, las dos salen con 0 y sin fallos por APIs de Node (solo se probó `--help`).

## Step 4: ¿cómo precargar la caché de Bun sin correr la herramienta?

Subcomandos disponibles en 1.4.4: `bun pm cache`, `bun pm cache rm|prune|pack|unpack`, `bun pm fetch`.

(a) `bun add @ramon-sg/github-rest@0.6.0` en un directorio temporal con caché vacía: la caché queda con `@ramon-sg/github-rest@0.6.0@@@1`. Luego, con el registro apuntado a un puerto cerrado:
```
BUN_CONFIG_REGISTRY=http://127.0.0.1:9 bunx --bun @ramon-sg/github-rest@0.6.0 --help
-> Resolving dependencies / error: ConnectionRefused downloading package manifest @ramon-sg/github-rest
```
(b) `bun pm fetch` (con la dependencia en `package.json`): "Fetched 1 package into cache". Mismo resultado con registro cerrado: `ConnectionRefused downloading package manifest`.

Respuesta: ambos llenan la caché de paquetes, pero `bunx` igual pide el manifiesto al registro, así que no dejan lista una ejecución sin red. Solo una corrida previa de `bunx` lo hace (ver Step 5). Con red, `bunx` tras (a) funciona. Precargar con `bun add` / `bun pm fetch` sirve solo para ahorrar la descarga del tarball, no para trabajar sin red.

## Step 5: ¿corre sin red desde la caché?

Tras una corrida previa de `bunx` en la misma caché (Step 3):
```
BUN_CONFIG_REGISTRY=http://127.0.0.1:9 bunx --bun @ramon-sg/github-rest@0.6.0 --help -> exit 0, imprime Usage
npm_config_registry=http://127.0.0.1:9 npx --yes @ramon-sg/github-rest@0.6.0 --help
  - caché de npm sin el paquete: ECONNREFUSED 127.0.0.1:9
  - tras correrlo antes con red: sin salida y tuvo que cortarse con timeout de 60 s (reintentos); con --prefer-offline tampoco dio salida en 60 s
```

Respuesta: `bunx --bun` corre sin red si el paquete ya se ejecutó antes con `bunx` en esa caché (versión exacta); `npx --yes` no es fiable sin red (falla o se queda reintentando).

## Step 6: paquete con dependencias empaquetadas

`probe` 0.0.1 con `picocolors`, empaquetado con `bun build cli.js --target node --outfile dist/cli.js` (bin a `dist/cli.js`, `dependencies` vacío, `files: ["dist"]`), `npm pack`.
```
npx --yes <tgz> probe           -> "sh: <tgz>: Permission denied" (npx toma la ruta como binario)
npx --yes -p <tgz> probe        -> node (exit 0)
bun add <tgz> + bun x --bun probe -> bun
```
En la caché de Bun (dedicada) solo quedó `probe`, sin `picocolors`; el log de npm no menciona `picocolors`. (La salida no lleva color porque no es TTY.)

Respuesta: sí, ambos corren con las dependencias dentro del bundle y sin bajar `picocolors`; con npx hay que usar `-p <tgz> <bin>`, no la ruta sola.

## Step 7: Bun en la nube de Claude

No se puede probar desde aquí. Comando a probar en una sesión en la nube:
```
npm i -g bun && bun --version && bunx --bun @ramon-sg/github-rest@0.6.0 --help
```

Respuesta: pendiente de probar en una sesión en la nube.

## Conclusión

`--bun` gana sobre el shebang, las dos herramientas reales corren con `bunx --bun` y los paquetes con dependencias empaquetadas funcionan igual con Bun y npx. Limitación: no hay forma de precargar la caché de Bun de modo que `bunx` funcione sin red; `agent-kitchen` no puede precargar con `bun add`/`bun pm fetch` para ese fin (solo ejecutando `bunx` una vez, lo que corre la herramienta).
